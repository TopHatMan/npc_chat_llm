# mod-npc-chat-llm

**mod-npc-chat-llm** is an experimental AzerothCore module that lets a real player speak to a targeted world NPC and receive an in-character LLM-generated reply.

The goal is not to turn NPCs into generic chatbots. The goal is to make Azeroth feel more alive: vendors, quest givers, guards, trainers, enemies, and strange one-off creatures should be able to respond like people who belong in the world.

This module was created for a private progressive AzerothCore / Playerbots realm and is being developed as a practical “living world” roleplay system.

## AI-assisted development note

This module was designed and built mainly through iterative work with **GPT** and **Claude**, with project direction, testing, debugging, and design decisions driven by the server owner/maintainer. AI tools helped generate and revise code, architecture, prompts, documentation, and debugging plans.

That means this repository should be treated as an actively tested, human-directed, AI-assisted project rather than a polished upstream AzerothCore module.

## Current status

**Status:** experimental / alpha  
**Target core:** AzerothCore WotLK 3.3.5a  
**Current API style:** OpenAI-compatible `/chat/completions` endpoint  
**Known working use case:** real player targets a nearby NPC, speaks in `/say`, and receives an NPC reply.

Current code keeps game-object access on the main thread and moves file I/O plus the LLM call onto a detached worker thread. Replies are queued and emitted later from `WorldScript::OnUpdate`, which prevents off-thread access to live AzerothCore objects.

## What it does right now

Current behavior:

- Listens for real player chat.
- Ignores bot sessions.
- Ignores dot commands such as `.tele`, `.npc`, `.debug`, etc.
- Optionally requires a prefix before NPC chat triggers.
- Requires the player to have a live creature selected.
- Requires the selected creature to be within configured range.
- Captures NPC identity data:
  - NPC name
  - entry ID
  - subname
  - level
  - gender
  - creature type
  - rank
  - NPC flags / role
  - zone name
  - whether the NPC regards the player as friend, stranger, or enemy
- Sends an OpenAI-compatible LLM request.
- Stores shared NPC history.
- Stores personal player-to-NPC history.
- Queues the reply safely back to the main thread.
- Emits the response as NPC speech.

## Planned prompt layout

The next design step is to move most prompt behavior out of C++ and into editable files.

Planned runtime prompt layout:

```text
AI_RP/
└─ npc_history/
   ├─ default.prompt
   ├─ shared/
   │  ├─ NPCName_Entry.history
   │  └─ NPCName_Entry.prompt
   └─ personal/
      └─ PlayerName_PlayerGuid/
         ├─ NPCName_Entry.history
         └─ NPCName_Entry.prompt
```

Prompt priority should be:

1. hardcoded identity and safety wrapper generated by the module
2. `default.prompt`
3. shared NPC prompt, if present
4. personal player/NPC prompt, if present
5. shared NPC history
6. personal player/NPC history
7. current player message

The idea is simple: the code should know **who** the NPC is, but the prompt files should control **how** NPCs behave.

## Planned command namespace

The planned in-game command namespace is:

```text
.npcc
```

The extra `c` stands for **NPC Chat** and avoids colliding with existing `.npc` command handlers.

Planned commands:

```text
.npcc reload
```

Reload NPC chat configuration and prompt files.

```text
.npcc reset
```

For a normal player: reset that player’s personal history with the targeted NPC.

For a GM: reset the targeted NPC’s shared history and all personal histories for that NPC.

```text
.npcc reset all
```

GM-only. Reset all NPC chat histories.

```text
.npcc prompt
```

Create a blank personal prompt file for the targeted NPC.

```text
.npcc prompt "prompt text here"
```

Create or replace the personal prompt file for the targeted NPC.

```text
.npcc prompt shared
.npcc prompt shared "prompt text here"
```

GM-oriented shared NPC prompt management.

```text
.npcc prompt default
.npcc prompt default "global prompt text here"
```

GM-oriented default prompt management.

## Planned hostile NPC conversations

Hostile NPCs are a special design case.

Friendly and neutral NPCs can use normal short-range conversation. Hostile NPCs should support a “parley at distance” mode so the player can speak to an enemy from outside aggro range before choosing to fight.

Planned hostile behavior:

- allow hostile chat only if enabled in config
- require a minimum distance so the player is not standing inside aggro range
- allow a larger maximum distance than friendly NPC chat
- force hostile replies to private/targeted delivery so the player can receive the response from far away
- inject prompt context that this is a tense exchange before combat, not a friendly conversation

Potential config:

```ini
NpcChat.AllowHostileChat = 1
NpcChat.FriendlyMaxDistance = 20.0
NpcChat.HostileMinDistance = 30.0
NpcChat.HostileMaxDistance = 100.0
NpcChat.HostileForcePrivateReply = 1
```

## API support

Current LLM support is intentionally minimal:

- OpenAI-compatible chat completions endpoint
- bearer token authentication
- model name
- max token setting
- temperature
- timeout
- raw extra JSON parameters

The module currently appends:

```text
/chat/completions
```

to the configured base URL.

## Threading model

The design rule is strict:

```text
Main thread:
  read player/NPC state
  copy primitive data
  queue replies
  emit NPC speech

Worker thread:
  file I/O
  history read/write
  LLM HTTP request
  no live game object access
```

This matters because AzerothCore game objects should not be touched from worker threads.

## Security notes

- Never commit API keys.
- Never commit private server secrets.
- Be careful with public repositories if config files contain keys.
- Prefer `.conf.dist` files with blank keys.
- Add real `.conf` files to `.gitignore`.

Suggested `.gitignore` entries:

```gitignore
*.conf
*.key
.env
AI_RP/npc_history/
```

Depending on how you want to manage prompt files, you may commit default prompt templates but ignore live history.

## Known limitations

Current limitations:

- prompt behavior is still mostly hardcoded in C++
- no `.npcc` command system yet
- no editable `default.prompt` yet
- no per-NPC prompt file loading yet
- hostile NPC “parley” mode is not implemented yet
- no quest-context injection yet
- no rate limiting or per-player cooldown beyond normal chat flow
- no persistent queue handling on shutdown
- normal NPC speech may not be visible at long range
